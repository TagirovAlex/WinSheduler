# Механизм обновления WinSheduler

Статус: проект, код не пишется. Решения требуют ADR.

## 1. Принятые решения

| Вопрос | Решение |
|--------|---------|
| Канал распространения | Сетевая SMB-шара, без GPO |
| Подпись | Сертификат Authenticode от AD CS |
| Кто обновляет | Администратор |
| Обязательность | Необязательное обновление |
| Публикация | Скриптом сразу после сборки релиза |
| Откат | 2 предыдущие версии MSI + резервные копии БД |
| Бэкап БД | Всегда перед обновлением, на шару в `backups` |
| GitHub | Простой релиз: tag, notes, MSI, SHA256; без update-манифеста |
| Шара | `\\intsrvfs\winsheduler` |
| Доступ к шаре | доменный пользователь `winsheduler` — full control на корень |
| Клиенты | чтение корня шары |

GPO/SCCM не используем. Встроенный механизм — удобство для администратора,
а не замена централизованному развёртыванию.

## 2. Схема

```
Администратор
  │ release.ps1 -UpdateShare \\fileserver\Updates\WinSheduler
  ▼
SMB-шара
  ├─ latest.json
  ├─ WinSheduler-2.1.3.msi      (подписан)
  ├─ WinSheduler-2.1.2.msi
  ├─ SHA256SUMS.txt
  └─ releases/v2.1.3.md

Клиент WinSheduler.UI
  │ 1. читает \\fileserver\Updates\WinSheduler\latest.json
  │ 2. сравнивает version
  │ 3. показывает «Доступна 2.1.3»
  │ 4. администратор нажимает «Установить»
  │ 5. копирует MSI локально, проверяет SHA256 + подпись
  │ 6. проверяет runningTaskCount
  │ 7. msiexec /i ... /qn (elevated)
  ▼
MSI: CloseUi → stop service → replace → start service → data preserved
  └─ helper перезапускает UI
```

Обновление — полным MSI (major upgrade). MSP/дельты не вводим: ~50 МБ
в локальной сети приемлемо.

## 3. Шара

Пример:

```
\\intsrvfs\winsheduler\
  latest.json
  WinSheduler-2.1.3.msi
  WinSheduler-2.1.2.msi
  SHA256SUMS.txt
  releases\
    v2.1.3.md
```

Права:
- чтение — клиентская группа (`Domain Users`/`WinSheduler Users`
  или `Domain Computers`, см. открытые вопросы);
- запись — только доменный пользователь публикации `winsheduler`
  (full control на корень шары);
- остальные пользователи не должны иметь возможность менять MSI/манифест.

`latest.json`:

```json
{
  "product": "WinSheduler",
  "version": "2.1.3",
  "url": "\\\\intsrvfs\\winsheduler\\WinSheduler-2.1.3.msi",
  "sha256": "…",
  "size": 52240781,
  "publishedAt": "2026-11-10T10:00:00Z",
  "mandatory": false,
  "minVersion": "2.1.0",
  "notesUrl": "\\\\intsrvfs\\winsheduler\\releases\\v2.1.3.md"
}
```

Правила:
- MSI сначала копируется на шару, `latest.json` обновляется **последним**;
- версии только `x.y.z`, совпадают с `ProductVersion`;
- `sha256` обязателен;
- старые MSI храним 2–3 версии для отката;
- манифест можно читать как обычный файл, без HTTP-сервера.

## 4. Параметр сборки и MSI

В `publish.ps1` / `scripts/installer/build.ps1`:

```powershell
-UpdateUrl "\\intsrvfs\winsheduler"
```

Сборка передаёт `-d UpdateUrl=...` в WiX.

MSI пишет:

```
HKLM\SOFTWARE\WinSheduler
  UpdateUrl = \\intsrvfs\winsheduler
```

UI:
- `UpdateUrl` пустой/нет → пункт «Проверить обновления» скрыт;
- непустой → пункт виден.

Публичное свойство MSI `UPDATEURL` можно переопределить при установке,
но значение по умолчанию задаётся при сборке.

## 5. UI

Пункт меню: **Справка → Проверить обновления**.

- Проверка вручную + фоном не чаще 1 раза в неделю (168 ч).
- Если версия актуальна — «Установлена последняя версия».
- Если новее — диалог: версия, размер, заметки, кнопки
  «Установить», «Открыть папку обновления», «Позже».
- `mandatory=false`: «Позже» доступно всегда, без навязчивых напоминаний.
- Так как обновляет администратор:
  - при отсутствии прав — сообщение «Требуются права администратора»
    и кнопка перезапуска через `runas` (существующий механизм);
  - установка только по явному нажатию.
- Перед установкой проверить `runningTaskCount`:
  - если задачи выполняются — предупредить, что служба остановится
    и задачи будут прерваны; предложить отложить.
- После установки helper-процесс перезапускает UI.

## 6. Публикация после сборки

Единый сценарий, чтобы не забыть выложить:

```powershell
./release.ps1 -Version 2.1.3 -UpdateShare "\\intsrvfs\winsheduler"
```

Скрипт запускается от доменного пользователя публикации `winsheduler`,
у которого есть full control на корень шары. Пароль не хранится в скрипте,
репозитории и документации: используется текущая доменная учётная запись.
Если сборка/подпись требуют другой учётной записи, шаги разделяются:
сборка/подпись — под технической учётной записью, копирование на шару —
под пользователем `winsheduler`.

`release.ps1` (или расширенный `publish.ps1`):
1. `verify.ps1` + `publish.ps1`;
2. подписать `WinSheduler.msi`, `WinShedulerSvc.exe`, `WinSheduler.UI.exe`
   сертификатом из AD CS (`signtool`);
3. проверить, что MSI подписан;
4. скопировать MSI на шару как `WinSheduler-<version>.msi`;
5. скопировать release notes;
6. сформировать `SHA256SUMS.txt`;
7. **последним** атомарно заменить `latest.json`;
8. GitHub — простой релиз: tag, release notes, MSI и `SHA256SUMS.txt`
   (update-манифест на GitHub не публикуется).

Если шара недоступна — релиз завершается ошибкой, чтобы не получить
«сборка есть, обновления нет».

## 7. Ресурсы шары

- Диск: ~50 МБ на MSI × 3 версии ≈ **150 МБ**.
- RAM/CPU: отдельных сервисов не добавляется, только файловая шара.
- Сеть: манифест ~1 КБ на проверку; MSI ~50 МБ на клиента.
  Для 100 ПК — ~5 ГБ на релиз, для 500 — ~25 ГБ, для 1000 — ~50 ГБ.
- Резервные копии БД — **всегда перед обновлением**, на шару:
  `\\intsrvfs\winsheduler\backups\<host>\<timestamp>-<version>\`
  (`scheduler.db`, `-wal`, `-shm`). Запись — администратору обновления,
  чтение — администраторам. Клиенты в `backups` не пишут.

## 8. Безопасность

- Шара: запись — только доменный пользователь публикации `winsheduler`;
  клиенты — только чтение. Пользователь публикации не получает лишних прав
  на сервере — только full control на корень шары `\\intsrvfs\winsheduler`.
- Клиенты должны иметь traverse/read на `\\intsrvfs\winsheduler`;
  иначе UI не увидит `latest.json`.
- MSI и бинарники подписываются сертификатом AD CS.
- UI перед запуском проверяет:
  - SHA256 из `latest.json`;
  - Authenticode-подпись MSI (`WinVerifyTrust`);
  - допустимость пути (`\\server\share`, без `..`).
- MSI копируется в локальный защищённый каталог перед установкой,
  а не запускается напрямую с шары.
- UAC: установка с согласия администратора.
- Логировать проверку/скачивание/установку; не писать секреты.
- Учитывать, что обновление останавливает службу и прерывает running-задачи.

## 9. Откат

Храним на шаре 2 предыдущие версии MSI и release notes (плюс текущую).

Варианты:
1. **Откат вручную** (рекомендуется):
   - остановить службу и UI;
   - сохранить `scheduler.db` в резервную копию;
   - удалить текущую версию (`msiexec /x`, `KEEPDATA=1`);
   - установить предыдущий MSI;
   - при необходимости восстановить БД из копии;
   - запустить службу/UI.
2. **Downgrade через MSI**:
   - `MajorUpgrade AllowDowngrades="yes"` позволит поставить предыдущую
     версию поверх текущей, но схема БД может быть уже новее;
   - применять только после проверки совместимости и с резервной копией БД.

Перед обновлением служба/инсталлятор должны делать резервную копию БД
(или это делает `release.ps1`/`rollback.ps1`). Откат — только администратор.

## 10. План внедрения

1. ADR: SMB-шара, формат `latest.json`, подпись AD CS, UX, откат.
2. MSI: параметр `UpdateUrl`, запись в реестр, MSI `UPDATEURL`.
3. Подпись: `signtool` + сертификат AD CS в `release.ps1`.
4. UI: пункт меню, проверка версии, диалог, проверка хэша/подписи,
   running-задач, UAC, helper перезапуска.
5. Скрипт публикации на шару + `latest.json` + ретеншн.
6. `rollback.ps1` + резервные копии БД.
7. Тесты: пустой `UpdateUrl`, битый манифест, hash mismatch, offline,
   running tasks, отказ UAC, старая/новая версия.
8. Пилот на 2–3 ПК, затем раскатка администратором.

## 11. Открытые вопросы

1. Шаблон/thumbprint сертификата AD CS, доступ публикующего пользователя
   к закрытому ключу.
2. Кому выдан read на корень шары: `Domain Users`,
   `WinSheduler Users` или `Domain Computers`?
3. Показывать пункт обновления не-админам или только администраторам?
4. Есть ли окно обслуживания, когда можно останавливать задачи?
5. GitHub — только tag + release notes + MSI/SHA256 (без update-манифеста),
   подтвердить состав ассетов.

## 12. Решения по релизу

- Проверка обновлений: раз в неделю, вручную — в любое время.
- Откат: 2 предыдущие версии.
- Бэкап `scheduler.db` — всегда перед установкой, на шару.
- GitHub — простой релиз: тег, notes, MSI и `SHA256SUMS.txt`.
  Update-манифест и `latest.json` — только на шаре.
