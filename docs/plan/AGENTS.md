# Правила работы агентов WinSheduler

Документ обязателен для всех агентов и людей, работающих над проектом.

## 1. Жёсткие ограничения

1. **Не выходить за пределы папки проекта.** Всё, что создаётся или изменяется, находится внутри корня проекта.
2. **Временные файлы — только в `./temp/`.** Каждый трек использует свой подкаталог: `./temp/<track>/`. Каталог `./temp/` исключён из git.
3. **Пути — только относительные, с прямыми слэшами:** `./temp/`, `./src/`, `./docs/`.
4. **Буквы дисков и обратные слэши в командах и документации запрещены.**
   Абсолютный путь допустим только как аргумент внешней утилиты и пишется с прямыми слэшами: `c:/Github/WinSheduler`.
5. **Команды запускать с корнем проекта как рабочим каталогом** (параметр `workdir`/`cwd`), а не через `cd`.
6. **Минимальный дифф.** Править только нужный кусок, соседнее не трогать. Попутный рефакторинг запрещён.
7. **Перед правкой — прочитать файл, после — проверить затронутый модуль.** Сохранять стиль и контракты.
8. **Язык:** комментарии в коде и конфигах, а также документация — только по-русски.
   При правке файла переводить только комментарии изменяемого участка; массовый перевод существующих английских комментариев запрещён (это нарушает минимальный дифф).
9. **Документация должна оставаться актуальной.** Если меняется поведение, контракт, команда или раскладка — обновить соответствующий документ в `./docs/`.

## 3. Рабочий процесс

1. Прочитать `./docs/plan/TASKS.md`, свой трек и относящиеся к задаче контракты в `./docs/contracts/`.
2. Взять первую задачу своего трека со статусом `[ ]`, у которой выполнены зависимости.
3. Прочитать затрагиваемые файлы целиком (или нужный участок), зафиксировать текущее поведение.
4. Внести минимальные изменения строго в своей зоне.
5. Обновить комментарии/документацию по-русски, если изменилось поведение.
6. Запустить проверку: `./scripts/verify.ps1 -Scope <track>` (или `./scripts/build.ps1` + `./scripts/test.ps1`, если scope ещё не реализован).
7. Записать статус в `./docs/status/<track>.md`: что сделано, что проверено, что осталось, какие есть блокеры.
8. Отчитаться по шаблону из раздела 6.

Запрещено:
- в общем рабочем дереве — делать `git commit`, `git checkout`, `git reset`, `git stash`, `git push`;
- в изолированном worktree своего трека разрешены `git add` только своих файлов и `git commit`; `git push`, `git checkout`, `git reset`, `git stash` запрещены везде;
- удалять или перезаписывать чужие изменения;
- трогать `./published/**` и любые пользовательские данные;
- менять контракты без ADR;
- добавлять зависимости без ADR;
- выполнять сетевые запросы и скачивания без явного разрешения;
- запускать разрушительные команды (`Remove-Item` вне `./temp/`, `format`, `sc delete` и т.п.).

## 4. Команды

Все команды выполняются из корня проекта, без `cd`.

| Команда | Назначение |
|---------|------------|
| `./scripts/build.ps1` | сборка C++ и C# |
| `./scripts/test.ps1` | тесты C# и C++ (если есть) |
| `./scripts/format.ps1` | проверка форматирования |
| `./scripts/verify.ps1 -Scope <track>` | полный локальный gate для трека |
| `./scripts/bench.ps1` | замеры производительности |

Сборки сериализуются общим lock-файлом `./temp/locks/build.lock`, чтобы параллельные агенты не портили `bin/` и `obj/`. Ожидание lock — до 10 минут, затем ошибка.

## 5. Definition of Done

Задача считается выполненной, когда:

- сборка зелёная (`./scripts/build.ps1`);
- тесты зелёные (`./scripts/test.ps1`);
- нет новых предупреждений компилятора;
- форматирование не нарушено (`./scripts/format.ps1`);
- затронутый модуль проверен вручную или тестом;
- документация и комментарии обновлены по-русски;
- security-чеклист из `./docs/contracts/SECURITY.md` соблюдён;
- бюджет производительности не ухудшен (если задача его касается);
- статус записан в `./docs/status/<track>.md`.

## 6. Шаблон отчёта

```
Задача: <ID>
Статус: готово / частично / заблокировано
Изменённые файлы:
- ./...
Проверка:
- ./scripts/verify.ps1 -Scope <track> — успешно/ошибка
Что осталось:
- ...
Блокеры:
- ...
```

## 7. Блокировки и конфликты

- Если задача заблокирована больше 30 минут — записать причину в `./docs/status/<track>.md`, пометить `[!]` и взять следующую независимую задачу своего трека.
- Если нужна правка чужого файла — не править, а создать запрос в `./docs/status/<track>-requests.md`.
- Если обнаружен дефект вне зоны — описать его в `./docs/status/<track>-requests.md`, не исправлять самостоятельно.
- Конфликт контрактов решает Architect через ADR.

## 8. Безопасность

- Секреты, пароли и токены не попадают в код, логи, тесты и документацию.
- Пароли не логируются; в логах — только факт наличия (`hasPassword`).
- Внешние пути валидируются по правилам `./docs/contracts/SECURITY.md`.
- Новые сетевые зависимости запрещены без ADR.
- SQL — только параметризованный.
- Перед коммитом Integrator проверяет отсутствие секретов в диффе.

## 9. Документация

- `./docs/plan/TASKS.md` — доска задач; правит только Integrator.
- `./docs/status/<track>.md` — статус трека; правит владелец трека.
- `./docs/contracts/**` — контракты; правит Architect.
- `./docs/adr/**` — решения; правит Architect.
- `./docs/status/gate.md` — результат локального gate; правит Gatekeeper.
- `README.md` и `SPECIFICATION.md` обновляются при изменении пользовательского поведения.
